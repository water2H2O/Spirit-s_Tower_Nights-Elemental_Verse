## 一、一次施法的完整数据流

```
仪式台三口                     申明板                    施法
──────────────────────────────────────────────────────────────
① 主料 ─┐
② 辅料 ─┼─▶ inputValue() ──▶ 匹配反应 ──▶ 现象 ──▶ 按形态分派
        │   （主料+辅料）      （至少包含）
③ 态   ─┴─▶ SpellParams（不进入 inputValue）──▶ 六参数
                │
                └─▶ 写入时把魔法名存进板子（客户端没有反应表）
```

| 环节 | 类 | 说明 |
| --- | --- | --- |
| 投入 | `RitualAltarBlockEntity` | 三口 × 每口 1/3/9 个 → 档 1/2/3 |
| 申明 | `Declaration` | 主料 + 辅料 + 态 + 魔法名 |
| 匹配 | `ReactionManager.match` | **至少包含**，取要求最多的那条 |
| 现象 | `Phenomenon` | type / element / amount / duration / cost |
| 参数 | `SpellParams` | 烈度 / 范围 / 持续 / 造拆 / 连锁 / 极性 |
| 分派 | `SpellCaster` | 按 `form` 走触摸 / 自生 / 弹射物 |

## 五、双板拼接（作者提出，待设计）

> **拼接 = 两块申明板 + 一种驱动材料 + 一种修饰元素。**

| 角色 | 谁 | 作用 | 类比 |
| --- | --- | --- | --- |
| 主体 | 申明板 A | 决定基础魔法 | 函数体 |
| 主体 | 申明板 B | 决定另一段魔法 | 函数体 |

## 七、元素权重表（2026-10-18 平衡后，唯一口径）

> **平衡原则（作者定）**：所有元素的强度压在 **1.0 ~ 2.5** 之间，
> 不允许任何一个"元素值特别高"。

### 基础元素

| 元素 | 元素值 | 强度 | 主成分 |
| --- | --- | --- | --- |
| 火 / 水 / 地 / 风 / 草 / 光 | 单轴 1.0 | **1.0** | 对应轴 + |
| 暗 | `{光:-1}` | **1.0** | 光 − |

### 二级元素

| 元素 | 元素值 | 强度 | 主成分 | 备注 |
| --- | --- | --- | --- | --- |
| 霜 | `{水:1, 火:-0.5}` | **1.5** | 水 + | 作者原定 |
| 烬 | `{火:1, 光:-0.5}` | **1.5** | 火 + | |
| 砂 | `{地:1, 水:-0.5}` | **1.5** | 地 + | |
| 芽 | `{草:1, 水:+0.5}` | **1.5** | 草 + | |
| 电 | `{风:1.5, 光:0.5}` | **2.0** | 风 + | |
| 晨 | `{光:1.5, 火:0.5}` | **2.0** | 光 + | |
| 影 | `{光:-1.5, 草:-0.5}` | **2.0** | 光 − | 负向也有强弱 |
| 木 | `{草:2}` | **2.0** | 草 + | 纯强化 |
| 冰 | `{水:1.5, 火:-1}` | **2.5** | **水 +** | 解决并列（原 1 vs -1 被判成负火） |
| 金 | `{地:2, 火:0.5}` | **2.5** | 地 + | 原 3.0 过高，已压到 2.5 |

### 三条设计约束（以后加元素也要守）

1. **强度上限 2.5**：否则"堆一个元素"就成唯一最优解
2. **避免并列**：主分量的绝对值必须**严格大于**任何修饰分量
   （冰原来是 `1 vs -1` 并列，结果由裁决顺序决定 —— 反直觉）
3. **负值是稀缺资源**：只有少数元素带负分量，正负才有意义

### 8.3 湮灭：以后不只光暗

因为现在**所有二级元素都是负值**（霜/冰 = 负火，砂/金 = 负水，芽/木 = 负地，电 = 负草，烬 = 负光），
所以任何"正 + 负"只要净值归零就能湮灭：

```
火 + 冰 = 0   → 湮灭
水 + 金 = 0   → 湮灭
草 + 木 = 0   → 湮灭
```

余热目前只有数值、没有阶段 —— 三级"推进一阶"要等阶段 06 的瘴素定义。

### 8.4 负值怎么写（反应表数据格式）

三种写法，都在 `data/elemental_verse/reaction/*.json` 里：

**① 负要求**：这条轴必须是负的，且不高于该值
```json
"consume": { "water": 3, "fire": -0.5 }
```
→ 水 ≥ 3 **且** 火 ≤ -0.5。冻结就靠这条：3 水 + 1 冰（冰是负火）。

**② 上限**：这条轴最多这么多
```json
"max": { "fire": 2 }
```
→ 火 ≤ 2。防止"水多、火也多"的组合误触发。

**③ 净归零**
```json
"consume": {}
```
→ 所有轴加起来是 0 才匹配（`Reaction.accepts` 里 `input.isZero()`）。

> 注意：`consume` 里的负值和 `max` 是两种不同的语义 ——
> `consume: {fire: -1}` 是"参与计分的要求"，会影响排序强度；
> `max: {fire: 2}` 只是门槛，不计分。

### 8.5 还没落地的两处规则

1. **单元素 / 双元素的判定**目前看 `consume` 有几条轴，改成负值后要改成看**投入向量**有几条轴 —— 否则"水3 + 火-1"会被当成单元素。
2. **灭火变成水的附属**：需要在 `dispatch` 前统一给水系法术挂一次 `douse`，而不是靠一条独立配方。
