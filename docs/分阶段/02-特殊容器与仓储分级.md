## 一、这一阶段要解决什么

**玩家视角的一句话：**

> 我现在有七种元素了，可它们全都塞在同一个箱子里，一起烂掉。
> 我得想办法让**该留的留住，该走的走掉**。

阶段 01 让"元素会坏"成立，但**玩家没有任何办法干预** —— 只能眼睁睁看着。
阶段 02 给他第一套**干预工具**，同时把光/暗从"换个贴图的元素瓶"变成**真正的另一种容器**。

| 阶段 01 的状态 | 阶段 02 之后 |
| --- | --- |
| 所有元素都装在同一个"元素瓶"里 | 光/晨 → **折射棱镜**；暗/影 → **聚影瓶**；其余 → 元素瓶 |
| 只能看着它坏 | 密封仓（慢一半）、冰冷链（慢 20%）、符文柜（近乎停滞但吃元素） |
| 箱子里的元素**完全不衰变** | 容器里也会衰变（这是阶段 01 留下的空档） |
| 死寂物质只能当方块摆着 | 有正经的建材变体与配方 |

## 三、A · 光/暗独立物品

### 3.1 载体归属

**元素不再都住在"元素瓶"里。** 载体由元素决定：

| 元素 | 载体 | 物品 ID |
| --- | --- | --- |
| 地 / 水 / 风 / 火 / 草 | 元素瓶 | `element_vial` |
| 砂 / 冰 / 电 / 木 / 烬 / 霜 / 金 / 芽 | 元素瓶 | `element_vial` |
| **光 / 晨** | **折射棱镜** | `refraction_prism` |
| **暗 / 影** | **聚影瓶** | `shadow_bottle` |

**实现方式**：`ElementType` 增加一个 `carrier()`，返回"这个元素该装在哪个物品里"。
三件物品共用同一套数据组件（`element` / `decay_timer`）与同一套衰变逻辑，
只是**载体不同**。衰变扫描因此要认三种物品，而不是一种。

> 这比"+两件新物品"更彻底：它让"容器"成为**数据的一等公民**，
> 以后再加容器（比如神器的能量池）只要扩 `carrier()`。

### 3.2 采集：光暗的门槛坐实

阶段 01 的光/暗只能从创造栏拿。现在给它们正经的采集方式，**而且门槛要能感到"难"**：

| 载体 | 采集条件 | 交互 |
| --- | --- | --- |
| **折射棱镜** | **白天、露天**（天空光 ≥ 12） | 手持右键空气 → 得到光元素 |
| **聚影瓶** | **亮度 ≤ 7** | 手持右键空气 → 得到暗元素 |

- 采集**有冷却**（提议 5 秒），避免站着狂点刷满
- 采集成功有音效与粒子（光：清脆；暗：低频）
- **冰 → 霜** 那条支线保持不变（对冰方块用空瓶）

> 这两个条件正好把设定里的"光暗是后期主料"落到手上：
> **你得先会造容器，还得在对的时间、对的地方用它。**

### 3.3 图标

已有的贴图机制直接扩展：棱镜 / 聚影瓶各自用 `custom_model_data` 分发两个形态
（光/晨 共用棱镜外形，暗/影 共用瓶外形，靠瓶内颜色区分）。

**生成脚本 `tools/generate-vial-models.py` 扩展到三套**，序号仍然从 `ElementType.java` 解析。

## 四、B · 仓储分级

### 4.1 系数（沿用总纲 2.4，只做两条）

| 存放方式 | 系数 | 本轮 |
| --- | --- | --- |
| 放地上 / 普通箱子 / 随身携带 | ×1.0 | 基准 |
| **冰 / 霜 3×3×3 范围内** | **×0.8** | ✅ 做 |
| **石制密封仓** | **×0.5** | ✅ 做 |
| 符文柜 | ×0.02 | ⏸ 阶段 03 |

**乘算**，多个修正相乘（比如密封仓周围还铺了冰 → 0.5 × 0.8 = 0.4）。

### 4.2 石制密封仓

**定位：主力仓储，便宜、能盖一片。**

| 项 | 设计 |
| --- | --- |
| 形状 | 一个方块，正面有"密封盖"的纹样 |
| 容量 | **9 格** |
| 系数 | **×0.5** |
| 打开 | 右键打开 9 格界面（跟箱子一样） |
| 漏斗 | **允许**（进也允许出） |
| 比较器 | 支持（读数 = 装载量） |
| 配方 | 石块 ×6 + 任意死寂物质 ×2 + 生铁 ×1（一个便宜的初阶货） |

### 4.3 冰的冷链

- 物品**放在方块容器里或地上**时，检查所处位置 3×3×3 范围内有没有 冰 / 霜元素方块
- 有 → ×0.8；多个不叠加（只判一次）
- **随身携带不享受**（背包里做 3×3×3 扫描既贵又难解释）

> 这条让"冰"这个衍生元素**独占"延缓衰变"**这个用途（总纲 2.7），
> 也给了玩家一个便宜但占地方的手段：**给仓库铺冰**。

## 五、C · 容器内的衰变（本阶段技术核心）

### 5.1 现在的问题

阶段 01 只扫了**玩家背包**和**掉在地上的物品**。所以：

- 放进箱子的元素 → **永远不坏**（这是个 bug，不是设计）
- 放上货架/漏斗里的 → 同样不坏

### 5.2 方案

**做法：维护"已加载区块"集合，做预算受限的轮转扫描。**

```
ChunkEvent.Load   → 记下这个 ChunkPos
ChunkEvent.Unload → 移除

每 100 tick（5 秒）：
    从集合里取下一批（最多 N 个区块，N 可配，默认 64）
    对每个区块：
        getBlockEntities() → 遍历实现了 Container 的方块实体
        → 逐格推进衰变（用 4.2/4.3 的系数）
```

- **轮转**：游标一直往前走，保证不会每次都扫同一批
- **预算**：`maxChunksPerSweep`（默认 64）可配，服主能按机器调
- **只读已加载区块**：卸载的照旧"世界停下就停下"，与阶段 01 的语义一致

### 5.3 风险（写在前面）

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **API 不确定性** | `ChunkEvent.Load` / `LevelChunk#getBlockEntities()` 的具体签名要现查 | 我在本地能编译 + 进游戏验证，不会盲改 |
| **性能** | 大基地可能有几百个容器 | 预算 + 轮转；先按 64/5s 做，实测再调 |
| **不该算的东西也算** | 比如玩家手里正在开的界面 | 统一按"容器里的物品"处理，界面只是视图，不额外计时 |

> **备选方案（如果性能或 API 太折腾）**：只让**我们自己的方块**（密封仓）tick 自己的内容，
> 普通箱子不管。这样实现简单得多，但"普通箱子 ×1.0"就没意义了 ——
> 我不建议这么退，除非实测真的撑不住。

## 六、D · 死寂物质：先给「尘」，再压成块

> 作者 2026-10-17 提出。**这一节是新增设计，需要你确认下面三点。**

现在的衰变走到尽头直接给一块方块 —— 太重、也太"整"了。
改成**先给尘，再压成块**：

| 物品 | 来源 | 用途 |
| --- | --- | --- |
| **死寂尘**（新）`dead_dust` | **衰变走到尽头时产出** | 4 个 → 1 个死寂物质方块 |
| 死寂物质（已有）`dead_matter` | 4 尘合成 / 挖回来 | 建材与合成基底 |

**配方**：4 尘（2×2）→ 1 块。

### 为什么这个改动好

- **损失感变轻**：一块石头变成四小撮灰，玩家能看见"还剩多少"
- **多了一级加工**：从原料到建材中间有一步，死寂物质不再只是"垃圾的终点"
- **量级也更像衰变**：一份元素 → 一份尘 → 1/4 块砖

### 顺手要改的：建材变体

死寂物质的建材变体（死寂砖）**本轮不做**，避免陷进台阶/墙那 40 种朝向 JSON 里。
现有的方块 + 4 尘压块已够用，等有了数据生成（datagen）再铺建材。

### 需要你确认的三点

| # | 问题 | 我的建议 |
| --- | --- | --- |
| **1** | **一摞 16 个瓶子一起走到尽头，给 16 个尘还是 1 个尘？** | **按数量给**（16 → 16 尘）。只给 1 个会让人觉得亏掉 15 个，是负反馈 |
| **2** | 尘要**按元素分**吗（土尘/水尘…）？ | **不按，只有一种尘** —— 呼应"死寂物质只有一种"，也省 7 套贴图 |
| **3** | 尘的**贴图**怎么办？ | 先用死寂物质贴图缩小/调色做占位，等你画 |

> 若第 1 条选"只给 1 个"，那衰变必须先**拆成单个**再计时（一次只腐化一个），
> 否则整摞会一次性消失 15 个。这条会影响实现方式，所以要先定。
